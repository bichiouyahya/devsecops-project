# SBOM: software bill of materials

Task 3 (Person B). Produced by the `sbom` job in `.github/workflows/build-security.yml`
on every pull request and push to `main`, and kept as the `sbom` workflow
artifact (`sbom.cdx.json`, 90 days).

## What the SBOM contains

`sbom.cdx.json` is a CycloneDX 1.7 JSON inventory of everything Juice Shop is
built from, generated by Syft 1.55.0 from the source tree. It lists about 1,170
components: 657 npm packages for the Node.js backend (from `package-lock.json`)
and 508 for the Angular frontend (from `frontend/package-lock.json`), plus the
GitHub Actions used by the pipelines. Each component has its name, exact
resolved version and a package URL (purl, for example
`pkg:npm/jsonwebtoken@0.1.0`) that vulnerability databases can match against,
the file it was found in, and its declared license (available for 1,153
packages: mostly MIT, then ISC, Apache-2.0, BSD and MPL-2.0). The SBOM header
records the tool that produced it and the commit SHA it describes, so each
SBOM can be traced back to one exact build. This is the component inventory
the EU Cyber Resilience Act asks manufacturers to keep in their technical
documentation: when a new CVE is published, we can answer "are we affected?"
by searching the SBOM instead of rebuilding or rescanning the project.

## Findings

- **Without a lockfile the SBOM is almost empty.** Juice Shop sets
  `package-lock=false`, and Syft run on the raw repository finds only 4
  components (the GitHub Actions), not a single npm package. The job therefore
  resolves the dependency tree first (`npm install --package-lock-only
  --ignore-scripts`), as the `sca` job does. Committing a lockfile would make
  the SBOM describe exactly what is shipped.
- **The SBOM can be scanned on its own.** `trivy sbom sbom.cdx.json` finds
  37 HIGH/CRITICAL vulnerabilities, the same count as the direct Trivy scan of
  the source in the `sca` job. The inventory alone is enough to assess the
  exposure, without access to the code.
- **Juice Shop already generates an SBOM inside its Docker build**
  (`npm run sbom` with `@cyclonedx/cyclonedx-npm` in the Dockerfile), but it
  stays inside the image. Our job publishes one per commit, where it can be
  reviewed, archived and scanned.
